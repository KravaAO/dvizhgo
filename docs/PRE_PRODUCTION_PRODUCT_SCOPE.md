# Product scope перед test-production

## Мета

Зробити DvizhGO зрозумілим для нового room host без пояснень у чаті,
безпечним для публічного тестового домену та вимірюваним без збору зайвих
персональних даних. Це не повна маркетингова платформа й не повна LMS.

## Межа релізу

У test-production входять лише такі ролі:

- **відвідувач** — читає публічну сторінку;
- **room host** — створює кімнату, збирає/редагує квіз, запускає активність
  і бачить агреговані результати своєї кімнати;
- **participant** — входить у кімнату за кодом та ім'ям.

Не входять у цей реліз: реєстрація користувачів, платежі, спільна бібліотека
квізів між host-ами, персональні кабінети, повноцінна AI-генерація на сервері
та складна BI-аналітика.

## Пріоритети

| Пріоритет | Результат | Чому до production |
|---|---|---|
| P0 | Поліпшена публічна сторінка та безпечна тимчасова адмінка | Перший досвід і контроль доступу. |
| P0 | Редактор вставленого квізу з валідацією | Host не має редагувати сирий JSON. |
| P0 | AI-бриф із topic/count зверху й уточнювальними питаннями | Зменшує кількість зламаних або нерелевантних квізів. |
| P0 | Мінімальні SEO, metadata та noindex приватних сторінок | Безпечна індексація публічного домену. |
| P0 | Мінімальні product events і екран usage-аналітики | Дає змогу перевірити, чи сервіс реально використовують. |
| P1 | Вбудований AI-виклик з сервера та ліміти | Після перевірки copy/paste AI flow. |
| P1 | Експорт аналітики CSV | Після накопичення перших даних. |

## 1. Публічна сторінка `/`

### Завдання

Поточна сторінка добре працює як екран входу, але її disabled-навігація та
мінімальна комунікація не пояснюють продукт новому host-у. Вона має залишитися
швидкою і вести до двох дій: **увійти за кодом** або **створити кімнату**.

### P0-склад

1. Hero у поточному DvizhGO-стилі: короткий value proposition, два CTA і
   підпис «без реєстрації для учасників».
2. CTA «Як це працює» веде на окрему публічну сторінку `/how-it-works` —
   покроковий візуальний гайд, а не короткий маркетинговий блок.
3. Секція форматів: self-paced quiz, ДВИЖ-ДУЕЛЬ, Flash Question. Не обіцяти
   функції, яких немає в релізі.
4. Коротка секція privacy: participant вводить лише ім'я та код кімнати;
   результати бачить host конкретної кімнати.
5. Футер: назва продукту, посилання «Як це працює», «Конфіденційність»,
   «Умови тестування»; сторінки можуть бути статичними.

### Стиль і доступність

- Зберегти наявні кольори, грубу сітку, Courier micro-labels, контрастні
  кнопки та DvizhGO-brand; не додавати сторонню UI-бібліотеку.
- На сторінці рівно один `h1`; усі CTA мають помітний focus state.
- Клавіатура має відкривати/закривати панелі входу та створення кімнати.
- Перевірити ширини 320px, 768px, 1440px і `prefers-reduced-motion`.

### Критерії приймання

- Новий користувач за 10 секунд розуміє, як створити кімнату або увійти.
- Disabled-навігації немає: вона або веде до реальної секції, або відсутня.
- Жодні admin/room URL не рекламовані як публічні.

### Сторінка-гайд `/how-it-works`

Сторінка будується з великих пронумерованих кроків у наявному DvizhGO-стилі.
Кожен крок має короткий заголовок, 1–2 речення інструкції та окремий image
slot. Скриншоти додаються пізніше без зміни верстки.

| Крок | Текст для користувача | Місце для зображення |
|---:|---|---|
| 01 | **Створіть кімнату.** На головній натисніть «Створити кімнату». | `static/images/guide/01-create-room.webp` |
| 02 | **Відкрийте лобі.** Скопіюйте код кімнати — його введуть учасники. | `static/images/guide/02-lobby-code.webp` |
| 03 | **Підготуйте квіз.** Оберіть готовий або задайте topic і кількість питань, створіть через ШІ та відредагуйте результат. | `static/images/guide/03-quiz-builder.webp` |
| 04 | **Надішліть код групі.** Учасник вводить код кімнати та своє ім'я на головній сторінці. | `static/images/guide/04-join-room.webp` |

Правила для image slots:

- формат WebP, бажаний розмір 1600×1000 або більший, співвідношення 16:10;

- до додавання зображень показувати стилізовану заглушку з номером кроку, а не
  порожній контейнер;
- на mobile зображення розташоване під текстом кроку.

## 2. Тимчасова адмінка room host

### Принцип

Адмінка не є глобальною панеллю всіх даних. Вона належить лише поточній room
і потребує host-session + password. Її призначення — керування заняттям,
бібліотекою квізів кімнати та мінімальною аналітикою.

### P0-склад

1. Єдина верхня навігація: **Лобі**, **Квізи**, **Аналітика**, **Вийти**.
2. У header завжди видно назву кімнати, код, статус (`lobby`, `active`,
   `finished`) та кількість присутніх.
3. Небезпечні дії (`Скинути`, `Завершити room`) потребують модального
   підтвердження з чітким наслідком; `Вийти` не скидає дані.
4. Login екран не повідомляє, чи існує конкретна кімната, і повертає нейтральну
   помилку при неправильному паролі.
5. Додати базовий rate limit на POST login на рівні Nginx або застосунку.
6. Усі admin-відповіді мають `Cache-Control: no-store`.

### Не робити в P0

- не створювати окремих account-ів host;
- не додавати багаторівневі права;
- не зберігати доступ до room у query string.

## 3. Редактор квіза та AI-бриф

### Проблема поточного інтерфейсу

Сторінка `/admin/quizzes` дозволяє вставити JSON, переглянути та зберегти його,
але після вставки host не може зручно виправити питання. Важливі параметри
(topic і кількість питань) заховані всередині великого prompt-а.

### Нова структура сторінки «Квізи»

```text
Header: Назва room · код · [До лобі]

Quiz setup strip (sticky на desktop)
  Topic* | Кількість питань* | Мова | Рівень | Формати | [Згенерувати інструкцію]

Ліва колонка: бібліотека квізів кімнати
Права колонка: AI brief / вставити JSON

Після parse:
  Назва квіза [редагується] · 12 питань · 4 single · 6 multiple · 2 true/false
  [Додати питання] [Зберегти чернетку] [Зберегти та обрати]
  Список accordion-карток питань з inline-редагуванням
```

### Setup strip — обов'язкові поля

| Поле | Тип | Правило |
|---|---|---|
| Topic | текст, 3–120 символів | обов'язкове; показується першим у prompt. |
| Кількість питань | number, 1–67 | обов'язкове; default 10; у верхній частині екрана. |
| Аудиторія / рівень | select + optional text | приклади: 7 клас, junior developers. |
| Мова | select | default `uk`. |
| Рівень складності | easy / mixed / hard | default `mixed`. |
| Типи питань | checkbox-group | default: single + multiple; true/false опційний. |
| Навчальна мета | textarea, optional | додається до prompt тільки якщо заповнена. |
| Обмеження / джерела | textarea, optional | наприклад, «лише матеріал уроку 3». |

Значення зберігаються локально як чернетка room host-а до явного очищення.

### Вставлення та редагування

1. Host вставляє JSON у textarea і натискає **Перевірити й відкрити редактор**.
2. Frontend показує parse errors із рядком/полем, а backend повторно валідовує
   payload перед збереженням.
3. Після успішної перевірки JSON перетворюється на редаговані картки.
4. Картка питання містить: type, текст, додатковий контекст, code, answers,
   correct, explanation, difficulty; можна додати, видалити, дублювати,
   змінити порядок.
5. `correct` редагується через radio для `single`/`true_false` і checkbox для
   `multiple`; індекси не показувати користувачу.
6. Над списком постійно видно назву, topic і лічильник `N / 67`.
7. Зберігати лише валідний квіз; незбережені зміни попереджають перед виходом.
8. Після save показати назву, кількість, час збереження та дію **Обрати для room**.

### Prompt для зовнішнього ШІ

Кнопка **Скопіювати інструкцію для ШІ** будує prompt із setup strip, а не
використовує статичний багаторядковий текст. Prompt має два режими.

```text
Ти — методист і автор квізів українською мовою.

Завдання:
- topic: «{topic}»
- кількість питань: {count}
- аудиторія: {audience}
- складність: {difficulty}
- дозволені формати: {types}
- навчальна мета: {goal_or_not_specified}
- обмеження/джерела: {constraints_or_not_specified}

Спочатку перевір бриф. Якщо topic, кількість питань, аудиторія/рівень або
навчальна мета не задані чи суперечать одне одному, НЕ створюй JSON. Постав
до 3 коротких уточнювальних питань українською у нумерованому списку.

Коли даних достатньо, створи рівно {count} питань і поверни ТІЛЬКИ один
валідний JSON-об'єкт у схемі DvizhGO. Не додавай Markdown або текст поза JSON.
```

Після цього додається технічна JSON-схема та чинні правила валідації. Не
просити ШІ «вгадувати» джерела або вигадувати факти; за нестачі контексту він
має уточнити його. У UI поряд із кнопкою показати: «Якщо ШІ поставить питання,
відповідайте в тому ж чаті; вставляйте сюди лише фінальний JSON».

### P1: серверний AI

Вбудований AI-виклик можливий лише після окремого рішення щодо провайдера,
ключів, бюджету й privacy. Потрібні: server-side ключ, per-host rate limit,
явна згода на надсилання тексту провайдеру, timeout/retry та usage events.
API-ключ ніколи не потрапляє у browser або prompt, що зберігається в клієнті.

## 4. Мінімальна usage-аналітика

### Відповідь на питання продукту

Аналітика P0 повинна показати: чи створюють room, чи учасники реально входять,
чи запускають квіз і чи завершують його. Вона не потрібна для стеження за
окремими учасниками.

### Події

| Event | Коли | Властивості |
|---|---|---|
| `landing_viewed` | відкрита публічна сторінка | referrer domain, user-agent family; без повного IP. |
| `room_created` | host створив room | room_id, source. |
| `participant_joined` | успішний join | room_id; без display_name. |
| `quiz_selected` | host обрав квіз | room_id, quiz_id, question_count. |
| `quiz_started` | activity стала active | room_id, question_count, mode. |
| `quiz_completed` | attempt завершений | room_id, answer_count, duration bucket. |
| `quiz_saved` | host зберіг квіз | room_id, question_count, source=`manual|ai_json`. |
| `ai_prompt_copied` | скопійовано prompt | room_id, topic_present, count. |

### Зберігання та екран

- Таблиця `usage_events`: `id`, `event_name`, `room_id nullable`,
  `occurred_at`, `properties_json`; індекси за `occurred_at` і
  `(room_id, occurred_at)`.
- Не записувати ім'я participant, текст відповідей, prompt, access token,
  повний IP або user-agent string.
- Retention: видаляти сирі події старші 90 днів; до тестового релізу це
  документована ручна задача або scheduled job.
- `/admin/analytics` показує тільки aggregate за 7/30 днів: visits, room
  created, joins, quiz started, quiz completed, completion rate і середню
  кількість participant-ів на room.
- Дані відображаються лише authenticated host-у для власної room; глобальні
  агрегати — лише через захищений operations access після окремого рішення.

## 5. Мінімальне SEO та index policy

### Публічні сторінки

- Унікальний `title` і `meta name=description` для `/`, `/how-it-works`,
  `/privacy`, `/terms`.
- Canonical URL через production hostname.
- Open Graph: `og:title`, `og:description`, `og:url`, `og:image`; використати
  підготовлене статичне зображення 1200×630, а не випадковий screenshot.
- `robots.txt`: дозволити лише публічні статичні сторінки.
- `sitemap.xml`: містить тільки публічні URL.

### Заборонити індексацію

- `X-Robots-Tag: noindex, nofollow, noarchive` для `/admin`, `/lobby`,
  `/quiz`, `/result`, `/activity` і всіх `/api/*`.
- Не включати room codes, participant names або результати у meta, sitemap,
  canonical чи публічні URL.

## 6. Порядок реалізації

1. Статичні policy-сторінки, metadata, robots/sitemap, Nginx `noindex` для
   приватних шляхів.
2. Публічна landing page у поточній дизайн-системі.
3. Setup strip, dynamic AI prompt і валідований редактор квіза.
4. Тимчасова навігація адмінки, confirmation flows, cache/rate-limit headers.
5. Usage event schema, repository/service, events та aggregate admin screen.
6. Responsive/accessibility QA, інтеграційні тести й manual test за test-prod
   доменом.

## Definition of done для test-production

- [ ] Усі P0-критерії вище реалізовані та протестовані на desktop і mobile.
- [ ] Editor не дозволяє зберегти невалідний квіз; JSON не є єдиним способом
  редагування після вставлення.
- [ ] Topic і number of questions завжди видно до генерації prompt-а та в
  редакторі.
- [ ] Prompt ставить уточнювальні питання за неповного брифу й створює JSON
  тільки після достатнього контексту.
- [ ] В адмінці немає глобальних даних інших room.
- [ ] Analytics не зберігає відповіді чи зайві персональні дані.
- [ ] Приватні URL не індексуються, а публічна сторінка має коректні metadata.
- [ ] Усі тести проходять; production smoke test включає WebSocket через Nginx.
